# Instruction and project workflow audit

The authorized instruction and workflow redesign is implemented. Project continuity now defaults to minimal guidance, with compact Markdown and optional Beads modes, one work-state authority, evidence of completion, and change-based handoff. The user chose to retire proofread instead of revising it. The original audit findings below describe the pre-change baseline; implementation and closeout are recorded at the end.

This audit covers instruction quality and autonomy (scope 1.3), workflow architecture including Beads (1.4), and maintenance (1.6). ## Proposed project-management architecture

Use one canonical location for work items and status, and a named location for goals, decisions, and evidence. A summary may link or derive from the work store; it must not become a second independently updated backlog.

| Mode | Suitable use | Minimum structure |
| --- | --- | --- |
| Minimal continuity | Small tools, maintenance, short tasks | Existing usage/scope documentation and shared agent guidance. Add a short current-state note only when future work needs it; keep current task state in an adequate existing tracker or small note. |
| Markdown continuity | Sustained solo work with modest dependencies | One compact work-state record containing next action, open work, blockers, completion evidence, and meaningful decisions. Split a specification or plan out only when it improves readability or review. |
| Beads task tracking | Projects with enough dependencies, interrupted work, or overlapping ownership to justify a database-backed queue | Beads owns task state and dependencies. Shared guidance names that authority; specs and evidence remain readable project artifacts. Define decision storage explicitly. Markdown summaries are projections, not an additional task store. |

The minimal mode is the recommended default. Existing projects with adequate larger structures should not be rearranged solely to match a new fashion. Bootstrap should fill demonstrated gaps, audit should examine the resulting continuity, and handoff should update only changed durable facts.

There is no basis in this static audit for replacing every skill with a harness feature. Distinct user-invoked workflows remain useful. Harness features, hooks, and measured activation are considered when their deferred scopes resume.

## Beads replacement assessment

Beads is a credible replacement for the task ledger and dependency portion of the suite. Its [versioned README](https://github.com/gastownhall/beads/blob/v1.3.1/README.md) describes ready-work queries, task claiming, hierarchy, JSON output, and Dolt-backed persistence. These address limitations of a manually maintained status table, but do not establish improved outcomes for this user's projects.

| Existing responsibility | Proposed Beads fit | What remains outside or requires a policy |
| --- | --- | --- |
| Open tasks, status, priority, blockers | Strong fit: issue state and dependencies | Completion must still cite actual evidence. |
| Phases and roadmap | Epics/milestones plus dependency edges can express executable work | A readable product or architecture narrative still helps humans review intent. |
| Next work and interrupted-session handoff | Ready-work query, claimed task, and task notes | A ready task is not automatically authorized or highest priority; the latest user instruction governs selection. |
| Decisions and rationale | Decision issue type and issue content offer a possible home | Decide whether consequential decisions live there or in project specs; do not maintain both as separate truths. |
| Scope, non-goals, architecture, source evidence | Linked project documents | The task database does not make sources authoritative or interpretations factual. |
| Parked ideas | Deferred state is available | Preserve the current distinction between speculative ideas and committed scope. |
| Audit and ingestion | Can receive resulting work and decisions | Still require judgment, provenance, and reconciliation; these workflows remain useful. |

The [v1.3.1 issue types](https://github.com/gastownhall/beads/blob/v1.3.1/internal/types/types.go) include decision and milestone records, deferred status, acceptance criteria, notes, and a close reason. A future mapping should preserve existing IDs as references and distinguish cancelled work from completed work through an explicit disposition rather than silently treating every closed issue as done. This mapping is a design proposal, not an exercised migration.

Adoption carries maintenance obligations beyond ordinary checked-in Markdown. [The backend guide](https://github.com/gastownhall/beads/blob/v1.3.1/docs/architecture/dolt.md) describes Dolt version pinning, separate database history, synchronization, and backups. A successful source-code push alone does not prove task data is backed up. [The release notes](https://github.com/gastownhall/beads/releases/tag/v1.3.1) identify proxied-server mode as the default since v1.3.0 and describe backup limitations; the versioned README instead calls embedded mode the default. That disagreement leaves the deployment assumption unresolved here.

[The setup guide](https://github.com/gastownhall/beads/blob/v1.3.1/docs/getting-started/ide-setup.md) documents conservative authority and broader team-maintainer policies, and says some integrations write vendor instruction files. Any future pilot should preserve this repository's shared-guide/import policy and existing limits on push and Git configuration. Upstream contributor guidance is not authority to push this repository. [The installation guide](https://github.com/gastownhall/beads/blob/v1.3.1/docs/getting-started/installation.md) documents workflow-context injection; that adds context overhead to compare when behavioral evaluations resume.

**Recommendation:** simplify the Markdown default now as a proposed design, and consider Beads as an opt-in replacement for executable work tracking. Defer adoption until a pilot and the necessary compatibility/storage checks are authorized. Do not build a second home-grown dependency graph to compete with Beads. Do not migrate this repository or change its package catalog merely to signal adoption.

### Future adoption criteria

A pilot should use one representative ongoing project and a pinned release. It should show task creation, dependencies, claiming, closing with evidence, and recovery in a fresh session. Confirm storage topology, backup/restore, worktree ownership, and where task data persists across machines before migration. These are future acceptance conditions; no runtime or behavioral evaluation was performed in this audit.

Migrate active work first; preserve completed history as an archive unless useful to carry forward. Record old-to-new IDs, counts, status/disposition mappings, evidence links, and unresolved blockers. At cutover, label the old work ledger archival and make Beads the sole work-state authority. Reversal must reconstruct active work and references into a readable record, then verify parity before switching authority back. A JSON export can assist interchange; it should not be assumed to replace a database backup.
